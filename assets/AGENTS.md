# Front end

`assets/` holds the browser's JavaScript and CSS sources: `assets/js/` the hooks and pure modules of the pages, `assets/css/app.css` the stylesheet, and `assets/vendor.lock.json` the pinned vendored packages. What the vehicle page shows and the events it exchanges with the server are in `lib/gobusgo_web/live/AGENTS.md`; this file maps the modules, the build, the stylesheet, the service worker, offline use, and the checks each file runs.

## Build

- `mix assets.build` writes the built files to `priv/static/assets/`, which git ignores. Run it when a change touches `assets/` or the classes in a template; CI runs it as its own job.
- `mix assets.setup` installs the esbuild and Tailwind binaries at the versions `config/config.exs` pins (`mix assets.tools` alone), compiles the application, and runs `mix gobusgo.vendor.fetch`, which downloads the vendored packages at the versions `assets/vendor.lock.json` pins.
- `assets/vendor/` holds the downloaded npm packages, inputs of the build, and `priv/vendor/` the downloaded archives, which the endpoint serves under `/vendor`. Git ignores both; `assets/vendor.lock.json` is checked in. The assets are fetched in a checkout, in CI, and in the image build, never when the application starts.
- A vendored package or archive changes version only through `mix gobusgo.vendor.update`, never by editing the lock file or a downloaded file, and an archive moves only to a commit the task is given. Adding one needs the justification the style guide requires of a dependency. Read `lib/gobusgo/vendor_assets/AGENTS.md`.
- The build bundles `app.js` with the vendored `pmtiles`, `fflate`, and `@protomaps/basemaps`, and copies MapLibre's three module files unbundled, because MapLibre starts its worker from the file beside its own. `mix gobusgo.assets.map_library` makes that copy as a step of `mix assets.build`, into the directory `GobusgoWeb.MapLibrary` names, which carries the version, so a file's address never holds another version's content.
- `mix gobusgo.assets.service_worker` is the last step of `mix assets.build`, and of `mix assets.deploy` with `--digested` after `mix phx.digest`. It bundles `assets/js/service_worker.js` to `priv/static/sw.js`, which git ignores, with `SERVICE_WORKER_BUILD` defined as `GobusgoWeb.ServiceWorker` gives: the paths the worker stores when it installs, the release, a hash over those files, and the content identifier of the basemap's fonts and sprites. A build whose stored files are unchanged is the same release.
- The web app manifest, `priv/static/manifest.webmanifest`, and its icons under `priv/static/icons/`, placeholders until the artwork is supplied, are checked in. The manifest's `background_color`, the installed app's launch screen, is the dark theme's page background, since the manifest holds one value (GOB-342).

## Stylesheet

- Tailwind collects class names from `assets/css/`, `assets/js/`, and `lib/gobusgo_web/`, and from no Markdown file, so a word in an `AGENTS.md` never adds a class to the build (GOB-350).
- `assets/css/app.css` names the surface style of the boxes over the map once, as custom properties: the `surface` class gives it to an element, and the same rule gives it to MapLibre's control groups and popups.
- The page has a light and a dark theme, named by the root element's `data-theme`. Under `dark` the stylesheet sets the dark values of every color the page sets and of the entries of Tailwind's palette the markup names, so the markup is the same in both themes, with text at a contrast of 4.5:1 or more (GOB-247).
- Under `forced-colors: active` the stylesheet draws the marks that forced colors removes again in system colors (GOB-313). Links and checkbox labels with the `inline-target` class meet the target size (GOB-312).
- The stylesheet gives the sheet, the surface boxes, the map controls, and the popups `touch-action: pan-x pan-y`, so a pinch that starts on them does nothing (GOB-343).
- The close button, `popup-alert`, `message-headline`, and `message-caption` classes are defined here. `data-connection` and `data-local-trip` on the root element switch what the offline page shows.
- A change to `assets/css/app.css` or a route chip runs `node test/scripts/css_accessibility_check.mjs` and `node test/scripts/route_chip_color_check.mjs`; a color or a pair added to the page is added to the check's list.

## Rules the modules share

- The hooks talk to the server only through `pageEvents(this)` of `page_events.js`, which pushes with `push({name, payload, onReply})`. While the connection is live every event goes to LiveView; otherwise the page answers for itself from the saved offline bundle, by `offline_answers.js` (GOB-272).
- No module hands the DOM a string as HTML, such as `innerHTML` or MapLibre's `Popup.setHTML`, since the names and texts the page shows come from agencies and providers; `node test/scripts/dom_text_check.mjs` fails on one.
- `stored_settings.js` is the one module that reads and writes local storage, with a schema version and a migration run once on first use, and every read synchronous (GOB-265). Its header is the contract of each key, its shape, its default, and what losing it costs the rider, the document a native app reimplements. The key names, the schema version, and the stored themes are in `stored_settings.json`, which the module, the root layout's head script, and the offline screen read.
- `connection_state.js` is the one owner of the connection state (GOB-235): `connecting`, `live`, or `offline` with a reason, `browserOffline` or `serverUnreachable`, read with `connectionState()` and announced with `gobusgo:connection-change`, and carried as `data-connection` on the root element. Its inputs are the `ConnectionState` hook, which LiveView alone mounts, `navigator.onLine` with its events, and the layout's render time. `connection_rules.js` makes a page offline at once in an offline browser and for a copy older than `CACHED_COPY_AGE_MS_MAX`, and otherwise after `JOIN_WAIT_MS` with no join; a join makes it live, and so does the browser's network coming back to a socket that stayed joined.
- When the state turns live from any other, the page drops its own trip's filter, sends the kept `stop-arrivals:close` events, and calls each hook's `whenLive` callbacks, which stand in for `reconnected` and also cover a socket that stayed joined.

## Offline

- `offline_schedules.js` saves, once the page has loaded and the browser is idle, the routing snapshots of the service dates that have not ended, at most two, each with its names file, and the current route and stop tile archive, in the Cache API at low priority, again every 30 minutes and when the browser comes back online (GOB-269, decided in GOB-233). It writes the bundle's own manifest, at `/offline-schedules/manifest.json`, then the saved index, which names that manifest's and the tile archive's paths, so the previous complete bundle stays in use until its replacement is complete. The setting is on by default, and turning it off clears the store. While on it asks the browser to keep the page's storage once per page (GOB-249, GOB-327).
- `offline_basemap_setting.js` saves the basemap's offline extract whole in a store of its own, `gobusgo-offline-basemap-v1`, while the "Save the map offline" setting is on, off by default (GOB-271), and deletes any other copy in it; turning it off deletes the store. It announces each change with `gobusgo:offline-basemap-change`. `offline_basemap.js` decides which archive the map draws: the saved extract while offline and holding the extract its basemap names, and the full archive otherwise. Fonts and sprites stay outside the setting.
- While offline the page answers `stop:position`, `trip:names`, `trip:filter`, `trip:clear`, and `vehicle-filter:restore` itself, the filter read-only; the other events get no answer, and the stylesheet says in place what needs a connection. A `stop-arrivals:close` while offline is kept, bounded, and sent once the page is live.
- `offline_service.js` draws the vehicles and the open stops' arrivals from the saved schedules while offline (GOB-234), by the pure rules of `scheduled_service.js`, through the hooks' own `handle` callbacks: the markers under `vehicle-markers:scheduled`, which replace every agency's, and each stop's arrivals under `stop-arrivals:arrivals`. A trip stands on the straight line between the stops of its hop, with the `scheduled` status and no heading; a stop's arrivals are each trip's next visit within OneBusAway's default window of 35 minutes. Nothing runs while the page is hidden, and the markers, chunks, and arrivals are bounded. When the page is live again the vehicle hook drops these markers and sends `vehicle-markers:ready`.
- Each placement records its time as the `gobusgo:scheduled-placement` measure. Measured on 2026-11-08 in headless Chrome with the network off, with snapshots of 112 routes and 306,080 connections on that date, at the view of the whole archive: 247 markers, each placement with one open stop's arrivals 1.8 to 4.4 ms, a minute offline 657 ms of script and 1,281 ms of tasks against 2,175 ms and 3,626 ms live, and a heap of 17.2 MB against 12.5 MB live; the full network's dates hold about twice those connections, which is not measured.
- `saved_snapshots.js` reads the saved snapshots' files from the Cache API alone, the service date running first. A trip's filter shown offline replaces the routes in `route_stop_tiles.js` and adds a summary line of its own, shown while the root element carries `data-local-trip`.
- `offline_boot.js` is the offline host of a cold start (GOB-273): a copy opened with no network mounts no hook, since LiveView mounts hooks only on a join, so while offline before the first join the host mounts each `[phx-hook]` element's hook itself, in document order, every one but `ConnectionState`. It sets up the tile archive's address and the filter's routes first, from the address's filter or the stored one, and runs the page's `phx-mounted` commands. LiveSocket's `onPatchStart` hands the page over: the host destroys its instances in reverse order before LiveView mounts its own, with no reload. A hook hands its state to the next hook of its element through `hook_handoff.js`, taken once.

## Service worker

- The worker answers each request by the caching plan of GOB-249: the release's stylesheet, script, and MapLibre's files from a cache named for the release, stored when it installs; the basemap's fonts and sprites from a cache named for the archive's content, stored on first use; the tile archives and routing snapshot files from the offline schedules' cache first, then the network, since each address holds one content; the basemap's offline extracts from the saved map's cache first and the full archives not at all; `/api/routing/manifest` from the network, then the offline bundle's own manifest, then the copy it stored (GOB-269).
- `/vehicles` comes from the network, and from the bare copy of `/vehicles` the worker keeps when the fetch fails, the server answers 5xx, or a wait passes, with the offline screen where it holds no copy; any other page from the network, with an offline screen when there is none. The bare copy holds no filter, and a successful answer to `/vehicles` with no query replaces it (`vehicle_page_copy.js`, GOB-273). A copy older than the session token's 14 days reloads once when the network is back.
- The worker handles nothing else: the LiveView socket, every request that is not a GET, and the basemap files.
- The Cache API refuses to store a 206 and the vendored pmtiles refuses a 200 longer than the range it asked for, so the worker answers ranges itself: `byte_range.js` slices a stored 200 into a `206`, a `416`, or the whole file. `saved_files.js` holds the bodies of the files read last and answers a saved file that neither the store nor the network gives with `503` and `gobusgo-offline: not-saved`, which the Trip tab reads as the schedules not being saved.
- The worker reads the offline schedules' cache and never writes it. On activation it deletes its own caches of other releases and other archive contents, and never a cache whose name it does not own.
- A new worker waits once installed, the page offers the reload, and a click has the worker take over and the page reload, so a page and its files come from one release; a page left open asks for a new worker every hour.
- Every open page shows the offer, and the worker one page has take over controls them all, so a click on the offer of another page, whose worker has already taken over, reloads at once. A click whose takeover has not come within `RELOAD_WAIT_MS` of `release_offer.js`, 10 seconds, enables the button again with a message that says the new version is still starting, and a takeover after that still reloads the page (GOB-351).
