# HTTP server and browser pages

`lib/gobusgo_web/` holds the Phoenix site on Bandit (the choice and its rationale are in GOB-17): the endpoint, the router, the controllers, the LiveView pages, the components, and the pure modules that turn the views into what a page shows. The vehicle page has a file of its own, `live/AGENTS.md`, and the JavaScript and CSS it runs are in `assets/AGENTS.md`.

## Files

- `endpoint.ex` and `router.ex` are the endpoint, with its static file plugs, and the router.
- `controllers/` holds the health, readiness, agency, routing manifest, address manifest, intersection manifest, OpenAPI document, and MCP controllers, `FallbackController`, and the error bodies `ErrorJSON` and `ErrorHTML`; `problem.ex` writes problem details.
- `mcp/` holds the MCP endpoint's pure modules: `mcp/server.ex` decides the status and body of a request, `mcp/message.ex` parses the JSON-RPC message, `mcp/revision.ex` resolves the protocol revision and checks a 2026-07-28 request's headers against its body, `mcp/methods.ex` answers each method, `mcp/origin.ex` decides on the `Origin` header, `mcp/error.ex` holds the JSON-RPC errors and their statuses, `mcp/server_info.ex` the name, capabilities, and instructions, `mcp/registry.ex` the tools and resources, and `mcp/tool.ex` and `mcp/resource.ex` their contracts. `mcp/tools/` holds the `find`, `vehicles`, `arrivals`, `alerts`, and `plan_trip` tools and `mcp/resources/` the two transit resources (GOB-389) and `mcp/resources/trip_app.ex`, the `ui://` resource of the trip planner app, whose HTML `mcp/trip_app_document.ex` writes and is pure (GOB-388); `mcp/answer.ex` shapes the transit tools' answers and is pure, `mcp/answer_cache.ex` holds them, and `mcp/stop_holds.ex` with `mcp/stop_holds/hold.ex` holds the stops `arrivals` asks the arrival source for. `public_cors.ex` is the plug that lets a page of any origin read the three manifests and the OpenAPI document.
- `live/` holds the LiveView pages: `home_live.ex`, the placeholder at `/`, `agency_live.ex`, the test page at `/agencies`, and `vehicle_live.ex` with `vehicle_live/`, the vehicle page.
- `components/` holds the layouts and the function components: `layouts.ex`, `panel_sheet.ex`, `vehicle_filter_form.ex`, `app_info_panel.ex`, `service_alerts_panel.ex`, `shared_vehicle_toggle.ex`, `connection_signal.ex`, `donation_button.ex`, and `message.ex`.
- `public_host.ex` turns the public host name into the endpoint's options, and is pure.
- `usage_hook.ex` is the mount hook that registers every page of the live session with the usage recorder, and `connection_facts.ex` validates what the browser connects with and is pure.
- `service_worker.ex`, `GobusgoWeb.ServiceWorker`, gives the service worker build its constants, and is pure; `map_library.ex` names where a page loads MapLibre from, a directory that carries the version `assets/vendor.lock.json` pins, read at compile time, and is pure.
- `basemap_sources.ex` names where a map page loads its basemap from, the library's address included, the view it opens with, and the bounds of the whole archive, and is pure.
- `map_extent.ex` gives the bounds a map fits to show a set of positions, and is pure.
- `vehicle_markers.ex` turns one agency's fetch into the markers a map page draws, each with its status and the texts of its lateness and next stop, and is pure.
- `route_lines.ex` turns the two route views into the lines of the tile archive, and `stop_markers.ex` a stop of the stop view into its marker and says whether a map that draws a set of routes draws the stop; both are pure.
- `transit_query.ex` answers, from the views, what the vehicle page and the MCP tools both ask: the agencies, the filter bar's tokens and suggestions, `find/1`, the vehicles a filter keeps, a stop's arrivals with their fetch, and the routing manifest body. It reads the views and changes nothing, and its `*_version/1` functions name the fetches an answer draws on. The page's `OpenStops` and its filter bar call it, so the page and the tools show one answer.
- `stop_arrivals.ex` turns a stop's fetch of the arrivals view and the vehicles of the vehicle view into the arrivals a page shows, and is pure.
- `service_alerts.ex` turns the two situation views into the current and upcoming alerts of the routes a filter keeps, and is pure.
- `filter_params.ex` reads a raw filter out of query parameters, a field's values separated by commas, and writes a filter as a query string.
- `agency_options.ex` and `route_options.ex` give the options of a filter by agency and by route, and `filter_bar.ex` the tokens and suggestions of the filter bar from them; all three are pure.
- `app_info.ex` holds the texts of the vehicle page's info panel, the data terms, and the license of each thing a page ships, and is pure.
- `route_stop_tiles.ex` and `route_stop_tiles/` are the route and stop tile archive.

## Routes

- The contract of every JSON endpoint, its path, methods, statuses, headers, and bodies, is `priv/openapi.json` for the public ones and `priv/openapi.private.json` for `GET /health` and `GET /ready`. `test/gobusgo_web/openapi_routes_test.exs` fails when the router and the documents name different routes, so a route added or removed changes a document in the same commit.
- `GET /health` is the image's liveness check, says nothing of the views, and is not logged. `GET /ready` is true once `Gobusgo.OneBusAway.Readiness` finds the views full, reads the views, starts no fetch, and is not logged. Both report `tiles`, the freshness of the current route and stop tile archive; the archive never changes the status or the code, so a failing tile build leaves the site served, and no destination is named (decided in GOB-229).
- The agency routes serve the current fetch of the agency view. The manifest routes under `/api` serve `Gobusgo.Routing.Snapshots`, `Gobusgo.Addresses`, and, read through `Gobusgo.Reader` on each request, the newest manifest the intersection builds store (GOB-361, GOB-363, GOB-364). The three manifests answer `GET` and `HEAD` with `access-control-allow-origin: *` from `GobusgoWeb.PublicCors`, so the trip planner app, in a frame of another origin, reads them (GOB-388); `GET` and `HEAD /api/openapi.json` answer the same header, with the exact bytes of `priv/openapi.json` that `GobusgoWeb.OpenApiController` reads when it compiles, a `no-cache` revalidation, and a strong `etag` of the body's SHA-256 (GOB-407); no other route sets a CORS header.
- `POST /mcp` is the MCP endpoint (GOB-393), written by hand over Phoenix and the built-in `JSON` module, behind the `:api` pipeline; see "MCP endpoint" below.
- `GET /` is a placeholder page, `GET /agencies` a test page that lists the agencies of the agency view's current fetch and updates when the view switches, and `GET /vehicles` the vehicle page (`live/AGENTS.md`).
- The LiveView socket is at `/live`, over WebSocket only.

## MCP endpoint

- The protocol sources, checked 2026-11-11: the 2025-11-25 and 2026-07-28 revisions of <https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http>, `.../basic/versioning`, `.../basic/index`, `.../server/tools`, `.../server/resources`, `.../server/discover`, and `.../server/utilities/caching`, and `https://modelcontextprotocol.io/specification/2025-11-25/basic/transports` and `.../basic/lifecycle`. The 2026-07-28 pages are a release candidate.
- `GobusgoWeb.McpController` reads the body, up to 1 MiB, and the `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` headers, hands them to `GobusgoWeb.Mcp.Server`, and writes its answer.
- A request is one of two eras. With no `MCP-Protocol-Version` header, or `2025-11-25`, `2025-06-18`, or `2025-03-26`, it is legacy: `initialize` (answered with the version the client asks for when it is one of the three, else `2025-11-25`), `ping` (removed in `2026-07-28`), tools/list, tools/call, resources/list, and resources/read, with no `initialize` required before the others since the server keeps no session. With `2026-07-28` it is modern: server/discover, tools/list, tools/call, resources/list, and resources/read, where `params._meta` holds the version and the client capabilities, the headers are checked against the body (`-32020`), a missing `_meta` field is `-32602`, and each result carries `resultType`, the server's name and version in `_meta`, and `ttlMs` and `cacheScope` for discovery, the lists, and `resources/read`. Any other version is `-32022` with the versions supported.
- A malformed body is `-32700` and a message that is not one request or notification `-32600`; an unknown method is `-32601`; an unknown tool, bad arguments, and an unknown resource are `-32602` (`-32002` for a legacy resource). A tool's `{:error, text}` is a result with `isError`. The JSON-RPC error keeps `application/json` under an error status through `GobusgoWeb.Endpoint.keep_json_content_type/1`.
- The tools and resources are the modules `config :gobusgo, GobusgoWeb.Mcp` lists under `:tools` and `:resources`: the tools `alerts`, `arrivals`, `find`, `plan_trip`, and `vehicles`, and the resources `gobusgo://api/agencies`, `gobusgo://api/routing/manifest`, and `ui://gobusgo/plan-trip`, whose text is the body `GET /api/agencies` and `GET /api/routing/manifest` answer (an unavailable agency view is the resource's internal error). A tool implements `GobusgoWeb.Mcp.Tool` (`definition/0`, `arguments_schema/0`, `call/1`) and a resource `GobusgoWeb.Mcp.Resource` (`definition/0`, `read/0`); `GobusgoWeb.Mcp.Registry` checks them when it is built, on every request, and lists them sorted by name and by uri. Adding one is a line of configuration.
- `GobusgoWeb.Mcp.ServerInfo.instructions/0` credits the data and links the terms from `GobusgoWeb.AppInfo`, the info panel's source of the same sentence.
- Every request, a `GET` included, is recorded through `Gobusgo.Usage.count/2` as a page connection of the page `mcp`, with the device class and browser family of its user agent and no identifier (`lib/gobusgo/AGENTS.md`, "Usage records").
- `GobusgoWeb.Mcp.Origin` decides on the `Origin` header, which the transport says a server must validate: a request with none proceeds, one that names the public host (`GOBUSGO_PUBLIC_HOST`, under any scheme and port, as the socket's check) proceeds, and any other origin, a malformed one, or a repeated header is refused with a JSON-RPC error, after the request is recorded. With no public host configured every origin proceeds, as the socket's does. The endpoint sets no CORS header: the host of an MCP App makes the request, not the app's frame.

### The trip planner app (GOB-388)

- The contract sources, checked 2026-11-11: the MCP Apps specification at revision 2026-01-26, <https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx>, and its page on CSP and CORS, <https://github.com/modelcontextprotocol/ext-apps/blob/main/docs/csp-cors.md>.
- `plan_trip` takes `to`, the rider's words, an optional `from`, the rider's words for where they are, and an optional `when`: `{mode, day, time}` with `mode` one of `now`, `departAt`, and `arriveBy`, `day` `today` or `tomorrow` (today when absent), and `time` a 24-hour `HH:MM` on the rider's clock, required unless the mode is `now`. The arguments go through `Gobusgo.Schema` as the endpoint does for every tool; the tool then refuses a blank `to`, an end over 200 characters, an unknown mode or day, and a missing or malformed time as a tool error the model can act on, and returns the fields given unchanged as `structuredContent`, with the text "Planning a trip from A to B.", or "Planning a trip to B." for a missing or blank `from`. A missing or blank `from`, or one such as "here", is a start at the rider's position: the app uses the device's location where the host grants it and otherwise asks the rider where they are (GOB-406); the tool's descriptions tell the model so. It resolves no place and routes nothing, so the server logs show the call and the file fetches and no search. Its description says that the journeys the app finds on its own reach the model as context, which the app sends as `gobusgo.journeys` by `ui/update-model-context` where the host declares `updateModelContext` (GOB-413), and that a journey the rider chooses replaces them. Its definition names the resource in `_meta.ui.resourceUri`.
- The resource is `ui://gobusgo/plan-trip`, of type `text/html;profile=mcp-app`, whose HTML `GobusgoWeb.Mcp.TripAppDocument` writes: one stylesheet and one script from the public origin by their digested names, `data-file-origin` naming that origin, a `main` the script fills, and the credits from `GobusgoWeb.AppInfo` (the transit data terms, OpenStreetMap and the ODbL, and the counties that give the addresses), with no inline script and no agency's name in its title. Its `_meta.ui` is on the listing and on the `resources/read` content, where the specification has a host read it: `csp.connectDomains` and `csp.resourceDomains` each hold the one origin, `permissions.geolocation` is requested, and `prefersBorder` is set. The origin is `https://` and the public host (`GOBUSGO_PUBLIC_HOST`), or `GobusgoWeb.Endpoint.url/0` with none. The CSP lists hold no other host, so the places, address, intersection, and routing files and the manifests must come from that origin.
- The server declares no extension. The specification has the host declare `io.modelcontextprotocol/ui` with the content types it renders in the client capabilities of its `initialize` and has a server check that before it registers a UI tool; this server keeps no session and lists the same tools to every client, so the tool always names its resource, and a host without MCP Apps shows the tool's text.
- What the app sends and reads, per the specification: the host sends `ui/notifications/tool-input` with the tool's arguments in `params.arguments` once the app's `ui/notifications/initialized` has arrived, and `ui/notifications/tool-result` with the tool's result as its params; the app reads the arguments from the first and, when they never come, the same arguments from the result's `structuredContent`. `assets/AGENTS.md` ("Modules") holds the app's modules, its requests to the host, and the journey object it sends.
- Three places where the texts differ, the first two settled by the specification and the third by its SDK types, which a host validates against: the handshake's request is `ui/initialize` with `appInfo`, `appCapabilities`, and `protocolVersion` (the specification's own `postMessage` sample writes `initialize` and `clientInfo`, which its lifecycle section and its SDK types contradict), and the model's context is `ui/update-model-context` with `content` and `structuredContent`, of which each request overwrites the last and a host may defer to the next user message; and `ui/message`, whose `params.content` is a list of content blocks, as the SDK's types give it, where the specification's prose shows one block, and whose result with `isError` true is a refusal.

### Transit tools

- Every answer is the REST shape, `data` and `meta` (`fetchedAt`, `requestId`, `count`, null where no fetch is behind the answer), as `structuredContent` and as the same JSON in one text block, each list at most 100 items (`GobusgoWeb.Mcp.Answer`). Every tool description opens with its purpose and carries the data credit and the link to the terms, from `GobusgoWeb.Mcp.ServerInfo.credit/0`, and every tool has an `outputSchema`.
- `find` takes `query`, cut to `GobusgoWeb.RouteOptions.query_length_max/0` as the filter bar's text is, and answers `agencies` and `routes`, the filter bar's suggestions under no filter, and `stops`, the stops whose name holds the text or whose code equals it (`GobusgoWeb.TransitQuery.find/1`). The page's filter bar has no stop search, so the stop half is new. `meta.restCount` and `meta.stopRestCount` count what the bounds left out.
- `vehicles` takes `agency` and `route`, each a list of identifiers judged by `Gobusgo.OneBusAway.VehicleFilter`: a filter the contract refuses is an `isError` result naming the field and the reason and no value. It answers the markers the page draws under that filter, in agency order, with `meta.fetchedAt` and `meta.requestId` of the oldest fetch they come from and `meta.fetches` naming each agency's.
- `alerts` (GOB-414) takes `route` and `stop`, each a list of identifiers judged by `Gobusgo.Filter` under a specification of those two fields, and needs at least one: a call with neither, or with only blank values, and a list the contract refuses are an `isError` result naming the field and the reason and no value. It answers `data.alerts`, the current alerts newest first and then the upcoming ones soonest first (the classification, seven-day horizon, and read-once rule of `GobusgoWeb.ServiceAlerts.matching/1`, which the alert panel's `alerts/1` shares), at most 100, each with `id`, `status` (`current` or `upcoming`), `summary`, `description`, `url`, `startsAt` (null for a current one), `activeWindows` (`fromMs` and `toMs`, null for an open end), and the `routeIds` and `stopIds` it names. An alert is kept when its affects name any given route or any given stop; the situation view records a stop only with a route at it, so an alert that names an agency and no route is left out, as on a page (the open decision in the root `AGENTS.md` stays open). The alerts are those the two situation views hold, the running trips' and the open stops', which the description says: a route with nothing running, or a stop no page or `arrivals` call holds, can have an alert the tool does not know. `meta.fetchedAt` and `meta.requestId` name the oldest situation fetch and `meta.restCount` counts what the bound left out. The tool starts no fetch and holds no stop.
- `find`, `vehicles`, and `alerts` start no fetch; before the agency view, the vehicle view, or either situation view holds a fetch they are an `isError` result asking for a retry, as the REST routes answer `503`.
- `arrivals` takes `stopId` and holds the stop through `GobusgoWeb.Mcp.StopHolds` before it reads. `data.status` is `arrivals` (with `meta` naming the stop's fetch), `fetching` (the stop is held and has no fetch; `data.retryAfterSeconds` is the arrival source's interval, `Gobusgo.OneBusAway.Sources.arrival_interval_ms/0`, so the next call after it finds the fetch the source made for the stop unless other due stops are ahead of it), `capacity_reached` (the stop is not held and no page holds it; `data.retryAfterSeconds` is the hold's length), or `unknown_stop`. A stop that a vehicle page holds is answered from its fetch at the cap.
- A hold is a process of its own, one per stop, under a `DynamicSupervisor` whose `max_children` is the cap, `GobusgoWeb.Mcp.StopHolds.hold_count_max/0`, 10. It holds the stop's key in `Gobusgo.Demand` for `Sources.vehicle_hold_ms/0`, 60 seconds, the time a page that goes away leaves its demand behind, and asking again renews it. The arrival source makes one request every five seconds whatever is held, so holds never raise the request rate to OneBusAway; they take room from the pages' stops in that one stream, whose refresh age grows with the count of open stops. Ten is the most for which one request per held stop, 50 seconds, fits inside a hold, which a test asserts.
- Each answer is held in `GobusgoWeb.Mcp.AnswerCache`, an ETS table of at most 256 entries cleared when a miss finds it full. The key holds the question and the identity of the fetches the answer draws on (`TransitQuery.find_version/0`, `vehicle_version/0`, `arrivals_version/1`, `alerts_version/0`: request identifiers, which change with `fetchedAt`), so a newer fetch finds no older answer. An arrivals key also holds the minute, because an arrival that has passed leaves the answer, and an alerts key holds it because an alert's window opens and closes with the clock.

## Response bodies and errors

- The bodies, statuses, and headers of a success and of an error are in the OpenAPI documents. A route whose view has no current fetch answers `503` problem details, never an empty `200`. `detail` appears only for an error whose explanation the application writes itself, so the message of an unexpected error never reaches a client.
- Every error under `/api` is problem details from `GobusgoWeb.FallbackController`, which answers the requests no API route matches. Elsewhere the error is an HTML page from `GobusgoWeb.ErrorHTML` for a request that accepts HTML first, and problem details otherwise.
- Plugs that can raise go in a router pipeline, never in the endpoint: the endpoint registers the callback that sets the problem media type, and only an error raised inside the router reaches the error renderer with that callback. `Plug.Static` is the one exception, because it runs before the router.

## Static files

The endpoint serves these through `Plug.Static` plugs, one per kind. A file they serve is answered before the request logger, so it leaves no log line.

- The service worker at `/sw.js`, with `cache-control: no-cache`, so a browser that checks for a new release never gets an old worker from a cache, and the built assets, `/manifest.webmanifest`, and its icons under `/icons/` at the root. Production serves these from the application through CloudFront once the gobusgo-infra change of GOB-250 is applied.
- The vendored archives under `/vendor/<archive>/<path>` from `priv/vendor`, cacheable for an hour. The one archive is `basemaps-assets`, the basemap's fonts and sprites.
- The basemap files under `/basemap/<name>` from `<GOBUSGO_DATA_DIR>/basemap`, through two plugs: every file whose name starts with `basemap-`, the archives and their offline extracts, cacheable for an hour, and `manifest.json`, revalidated on every use. A request with a `range` header gets `206` with that part of the file, which is how a PMTiles reader reads tiles. The pages and the archives share one origin, so no CORS header is set.
- The route and stop tile archives under `/tiles/<path>` from `<GOBUSGO_DATA_DIR>/tiles`, with ranges, cacheable for a year as immutable since each archive's name is that of its own build. The year is `GobusgoWeb.RouteStopTiles.reader_keep_seconds/0`, which the plug's header and every build's write both read; a file that is not there answers the router's 404. With a bucket the archives are in S3, each stored with that `Cache-Control`, and production serves `/tiles/*` from the bucket through CloudFront (GOB-218, GOB-221).
- The routing snapshot files under `/routing/<path>` from `<GOBUSGO_DATA_DIR>/routing`, cacheable for a year as immutable, since each file's name holds the SHA-256 of its content. With a bucket the files are in S3, and production serves `/routing/*` from the bucket through CloudFront.
- The places file under `/places/<name>` from `<GOBUSGO_DATA_DIR>/places`, through two plugs: every file whose name starts with `places-`, answered as the gzip stream it is stored as, `application/gzip` with no content encoding, cacheable for a year as immutable since the name holds the SHA-256 of the stream, and `manifest.json`, which names the current file, and `NOTICE.txt`, the license notice, as `text/plain; charset=utf-8`, each with `no-cache` and an `etag`. With a bucket the files are in S3 and production serves `/places/*` from the bucket through CloudFront (GOB-366; `lib/gobusgo/places/AGENTS.md`).
- The intersection files under `/intersections/<name>` from `<GOBUSGO_DATA_DIR>/intersections`, the files whose name starts with `intersections-`, each answered as the gzip stream it is stored as, `application/gzip` with no content encoding, cacheable for a year as immutable since the name holds the SHA-256 of the stream; the manifest in that directory is not served from it but at `/api/intersections/manifest`. The files are a derivative database of OpenStreetMap, offered under the ODbL. With a bucket the files are in S3 and production serves `/intersections/*` from the bucket through CloudFront (GOB-364; `lib/gobusgo/intersections/AGENTS.md`).
- The address shard files under `/addresses/<path>` from `<GOBUSGO_DATA_DIR>/addresses`, each answered as the gzip stream it is stored as, `application/gzip` with no content encoding, cacheable for a year as immutable, since each file's name holds the SHA-256 of its stream (`lib/gobusgo/addresses/AGENTS.md`). The year is `Gobusgo.Addresses.reader_keep_seconds/0`, which the plug's header and every build's write both read. With a bucket the files are in S3, and production serves `/addresses/*` from the bucket through CloudFront once the infrastructure change of GOB-365 is applied.
- The shared vehicle files under `/shared-vehicles/<path>` from `<GOBUSGO_DATA_DIR>/shared-vehicles`, each answered as the gzip stream it is stored as, `application/gzip` with no content encoding, which the browser expands with `DecompressionStream`, so the same bytes reach a page from the local directory and from S3. A cache may keep each as immutable for 60 seconds, which keeps no copy past the ten minutes Lime's terms allow. Production needs a CloudFront behavior for `/shared-vehicles/*`, which the infrastructure repository does not have yet (GOB-258).

## Compression

Every response leaves compressed when the client accepts it. Bandit compresses the bodies the application sends, and the LiveView socket offers per-message deflate. The built assets and the vendored files are answered with the gzip copy beside them, `<file>.gz`, which `mix phx.digest` writes for the built assets, `.mjs` included through `config/config.exs`, and `mix gobusgo.vendor.fetch` writes for each `.json`, `.pbf`, and `.txt` file of an archive. The basemap archives are sent as they are, because their tiles are compressed inside them and a range response carries no encoding.

## Browser pages

- Browser pages are LiveViews routed through the `:browser` pipeline, in one live session, rendered inside `GobusgoWeb.Layouts.root/1`.
- The root layout titles a page from its `page_title` assign as "<`page_title`> · Gobusgo", or "Gobusgo" alone for a page that names none (GOB-306).
- The root layout names the build's commit in `<meta name="revision">`, the WHATWG MetaExtensions name, where the build names one, and the render time in UTC to the millisecond in `<meta name="gobusgo:rendered-at">`, from which the browser tells a copy from a cache.
- The root layout runs an inline script before the stylesheet that sets the root element's `data-theme` from the stored theme setting, and the content of its one `theme-color` meta element to that theme's page background, so the first paint and the browser's status bar and overscroll are in the rider's theme whatever the system's mode (GOB-342). It links the web app manifest and the home screen icon, and ends the body with the hidden offer to reload into a new release.
- The live session's mount hook, `GobusgoWeb.UsageHook`, registers each connected page with the usage recorder, so a page added to the session is recorded with no code of its own, under its module's name in snake case less `_live`. A page mounts whatever the recorder answers.
- The browser connects with `client.viewport_width`, `client.language`, and `client.referrer_host`, which `assets/js/app.js` sends and `GobusgoWeb.ConnectionFacts` validates; the socket hands the page the user agent and the address it connected with.
- Every page holds the element of the `ConnectionState` hook, from `GobusgoWeb.ConnectionSignal.state_hook/1`.
- Where `GOBUSGO_DONATION_URL`, read by `Gobusgo.Config.donation_url/0`, names an `https` address, every page shows the donation button of `GobusgoWeb.DonationButton`, a link named "Support gobusgo on Ko-fi" that opens in a new tab with `rel="noopener noreferrer"`. The page requests nothing from the donation site until the rider follows it. With the variable unset or blank no page shows it, and a value that is not an `https` address with a host stops the application at startup. `GET /` and `GET /agencies` hold the button in a `<header>`, so it stands in a landmark.
- A status or error message is a bold headline that states the state and a muted caption with the next step or the detail (GOB-327): `GobusgoWeb.Message` renders one on the server and `assets/js/message.js` in the browser, the headline ending in a visually hidden full stop, so a live region reads two sentences.
- A page shows a value from outside the application as a link only when it is an `http` or `https` address.

## Session and origin

- The session is a signed cookie. `SECRET_KEY_BASE` supplies the secret: production refuses to start without it, and development and test generate a random one at startup when it is unset. The signing salts in the code are not secrets.
- `GOBUSGO_PUBLIC_HOST` names the host pages are served on: with it set the socket accepts a page of that host under any scheme and port and refuses every other origin, and production refuses to start without it. With it unset, outside production, the socket accepts any origin.
- The endpoint's generated URLs take the host and no scheme or port, because nothing generates an absolute URL.

## Route and stop tile archive

- `GobusgoWeb.RouteStopTiles` is a PMTiles archive of the lines and stops a map page draws with no filter, stored through the writer at `tiles/route-stops/dt=<date>/route-stops-<UTC time>-<SHA-256 of its features>.pmtiles`, and the process, started on every start, that holds the current archive's destination and the hash of its features. The vehicle page draws its lines and stops from it (GOB-219).
- After a start it finds the newest stored archive with `Gobusgo.Reader.discover/2` and reads both from its name, so a start from the same views builds nothing (GOB-277); an archive whose name holds no hash leaves it unknown and the first check builds. It logs `Route stop tiles discovery failed` at `warning` when it cannot.
- Its scheduler, where the sources are scheduled, checks every ten minutes and builds only when the hash of the features it would write differs from the current archive's (GOB-222), or when the current archive is a day less than its retention old, so the retention never deletes the archive a page points at (GOB-226).
- `freshness/1` judges an archive current or stale against that renewal age, `GobusgoWeb.RouteStopTiles.Build.renewal_age_seconds/0`, by the build time its name holds, and is pure; `/ready` reports it.
- `route_stop_tiles/build.ex` is one run: it reads the views, writes the features of `route_stop_tiles/features.ex`, which is pure, runs tippecanoe on them with a deadline, stores the archive, and logs `Route stop tiles built` at `info` or `Route stop tiles not built` at `error`. Without tippecanoe a build logs its failure and the application runs on.
- A route's feature holds `routeId`, `color`, `shortName`, `longName`, and `agencyName`. A stop's, from zoom 14, holds `stopId`, `name`, `code`, `direction`, `routes`, `agencies`, `routeIds`, and `routeChips`: each named route's name and CSS color as a JSON list of pairs, and its drawn routes with a comma before, between, and after them, so a layer filter matches the substring `,<id>,`.

## Tests

Tests send requests through the endpoint with `Phoenix.ConnTest` and mount pages with `Phoenix.LiveViewTest`; no socket is opened and no test runs the JavaScript. `test/gobusgo_web/accessibility/rendered_pages_test.exs` renders the browser pages and checks them against `Gobusgo.Test.Accessibility`, as the root file's toolchain section describes.
