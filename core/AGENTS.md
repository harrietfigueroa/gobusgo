# Rust core

`core/` is the Cargo workspace GOB-419 ports the logic of `assets/js/core/` into, so the web page and the native iOS and Android apps run one library. It holds three crates: `gobusgo-core`, the logic itself, and its two bindings, `gobusgo-core-wasm` for the web and `gobusgo-core-ffi` for Swift and Kotlin. Each exports `core_version`, the version of the core a binding was built from, and the modules ported so far: the assertions and the math of `assets/js/core/assert.js`, `assets/js/core/math/geodesy.js`, `assets/js/core/math/angles.js`, `assets/js/core/math/checks.js`, and `assets/js/core/math/interpolation.js` (GOB-425), the readers of the published binary formats of `assets/js/core/routing_snapshot.js`, `assets/js/core/packed_container.js`, and `assets/js/core/trip_path.js` (GOB-426), the walk of `assets/js/core/routing_walk.js`, the start stops near a rider's position, and the connection scan of `assets/js/core/routing_engine.js`, its `route` and `routeArrivingBy` (GOB-427).

## Rules

- **Pure, synchronous, no IO.** `gobusgo-core` takes values and returns values: it reads no file, clock, or network, holds no handle, and starts no work that finishes later. A query is a `start` and `resume` pair that a platform's driver calls with the files it fetched, as `assets/js/core/AGENTS.md` describes for the JavaScript.
- **No third-party crate in the core.** A platform's driver expands the gzip files with the zlib or `DecompressionStream` it already ships and hands the core the expanded bytes. The bindings take one crate each, wasm-bindgen and uniffi, the only way to reach each platform.
- **A binding holds no logic.** Each export converts its arguments and result across its binding and calls `gobusgo-core`.
- **A programmer error crashes with a message.** The workspace's lints in `Cargo.toml` deny `unwrap`, `expect`, a bare `panic!`, and the implicit panics of indexing, slicing, and arithmetic, so a failure goes through `gobusgo_core::assert::condition` or `gobusgo_core::assert::unreachable` with a message at the site, as `assert.js` keeps the JavaScript's: a condition assertion writes the operand values into its message, only when it fails, and every assertion panics with one payload, `AssertionError`. `assert::number_text` writes a number as JavaScript's `String` writes it, so a failure's message reads the same from both cores. The release profile aborts on a panic and checks overflow.
- **A failure crosses the web binding as an `AssertionError`.** The binding's panic hook throws its own `AssertionError`, a JavaScript `Error` that `assertionErrorClass()` returns, with the panic's message, and asks wasm-bindgen to make the instance anew before the next call, since the throw leaves the panic unfinished. Every argument crosses as a `JsValue` and is read inside the call, and every function the binding imports from JavaScript, the ones that build a result included, is marked `catch` and called through one helper, so an exception JavaScript throws during a call becomes the same failure and goes through the same renewal; an exception that unwound through the module would skip the hook and keep a slot of wasm-bindgen's table of JavaScript values, and once its 1,024 slots are taken every export fails. The conformance suite's `tools/conformance/tests/refused_calls.test.mjs` repeats each read JavaScript can make throw 1,100 times and then decodes a file: a number must be one, where wasm-bindgen's conversion would coerce a string or `null`, and text is read with `String`, as the JavaScript writes it into a message. No export takes a `&str`, which wasm-bindgen 0.2.130 copies into the old instance's memory before the call makes the instance anew. A native app aborts on a failure.
- **A result crosses the web binding as copies.** A file's bytes are copied into the module's memory once per call, and its columns leave as typed arrays copied out of it, since a view of the module's memory goes stale when the memory grows. A column of strings leaves as one text and the UTF-16 offset each string ends at, which the binding's JavaScript slices apart, where each string crossing alone costs a decode of its own. The binding's JavaScript builds the objects a JavaScript module returns, the `kind` of a result included, from those copies and the names the core gives each outcome, so a result has the module's shape and its outcome kinds have the module's names.
- **The readers exist in both cores until their callers move.** The routing snapshot, packed container, and trip path readers stay in JavaScript beside their Rust port. The vehicle page's `assets/js/saved_snapshots.js` and `assets/js/where_to_files.js` decode with the Rust routing snapshot reader, and `assets/js/names_stream.js` takes its `DecodeKind`, through the facade, `assets/js/core.js` (GOB-440), by the `default` esbuild profile's alias of the shell's specifier of `assets/js/core/routing_snapshot.js` (GOB-426); the page's trip planning, which decodes through `assets/js/core/routing_journeys.js`, the MCP apps' bundles, which load no facade, `assets/js/departure_files.js` among their modules, and the core's own modules, which import the reader by a relative path, run the JavaScript. The callers of the packed container and trip path readers stay on the JavaScript. The conformance suite runs the cases of `test/fixtures/routing/v2/` and `test/fixtures/one_bus_away/trip_path/` against both in three browsers, and `cargo test` runs them and those of `test/fixtures/packed/core-v1/` against `gobusgo-core`; a change to one copy is made to the other in the same commit.
- **The walk exists in both cores.** `assets/js/core/routing_walk.js` stays in JavaScript beside its Rust port, `core/gobusgo-core/src/routing_walk.rs`, and every caller runs the JavaScript: `assets/js/core/routing_journeys.js` and `assets/js/core/point_journeys.js` import it by a relative path, and `assets/js/trip_walks.js` by its specifier, which no esbuild profile aliases. The conformance suite runs the cases of `test/fixtures/routing/walk-v1/` against both in three browsers, and `cargo test` runs them and the refusals of `tools/conformance/tests/routing_walk.test.mjs` against `gobusgo-core`, each refusal with the JavaScript's message; a change to one copy is made to the other in the same commit.
- **The engine exists in both cores.** `core/gobusgo-core/src/routing_engine.rs` ports `route` and `routeArrivingBy` of `assets/js/core/routing_engine.js`, which stays in JavaScript beside it, and both bindings export the port, but every caller runs the JavaScript, which `assets/js/core/routing_journeys.js` imports by a relative path; the facade exports no engine, and no esbuild profile aliases it. The conformance suite runs every query of `test/fixtures/routing/engine-v1/expected.json` and each refusal of `tools/conformance/tests/routing_engine.test.mjs`, by its exact message, against both in three browsers, and `cargo test` runs them against `gobusgo-core`, each query labeled by its case's and its own name; a change to the engine in one copy is made to the other in the same commit. Where the JavaScript sizes a query's per-trip state by the largest trip index plus one, the Rust numbers the trips the connections name from 0 when the engine is built, so that state is bounded by the connection count, and `route` and `route_arriving_by` refuse a view with no link offsets, whose columns disagree in length, whose `departure_stop`, `arrival_stop`, `to_stop`, or `incoming_from_stop` column names a stop at or past its stop count, whose incoming link offsets differ in count from its outgoing ones, whose link offsets or incoming link offsets decrease or end anywhere but their link count, whose trip count exceeds its connections, whose connections are out of departure order, or whose `trip_slot` column holds a slot at or past its trip count, reading the departure, trip slot, and four stop columns whole on every query, a pass over every connection and link where the scan reads only its window, since an `EngineView`'s columns come from its caller on each call; `Engine::new` refuses connections out of departure order, walking links out of the order of the stop they leave, and a stop at or past the stop count, where the JavaScript answers from them as they are.
- **The engine crosses each binding in the shape its platform calls it.** The web binding's `createEngine` builds an `Engine` once and returns copies of what a query reads as a plain object of typed arrays: `connections` (its `tripSlot` numbering each connection's trip densely, where the JavaScript's engine holds `trip` and `sequence`), `links`, `incomingLinks`, `tripCount`, and `minimumTransferS`. It holds nothing across calls: `route` and `routeArrivingBy` take that object back, copy its columns into the module's memory, and borrow them into an `EngineView` without building the links again, so the renewal of the instance after a failure loses no engine. An engine one core builds is not one the other core's `route` takes. The uniffi binding's `RoutingEngine` is the one binding object that holds state: a `uniffi::Object` owning the `Engine` its constructor builds, whose `route` and `route_arriving_by` borrow its view. A uniffi record is serialized on every call, so an engine handed back as one would cross twice a query, and a native failure aborts the app, so no object outlives a failure.
- **The packed container is internal to the core.** No binding exports `packed_container`, apart from the web binding's `packedOutcome()` and `packedRefusal()`, its outcome and refusal names: each reader of a format built on the container gets its own export that takes the file's bytes and returns its records, and the browsers cover the Rust container through those readers. `assets/js/core/packed_container.js` stays while `assets/js/address_file.js`, `assets/js/intersection_file.js`, and `assets/js/place_file.js` read containers with it.
- **The web keeps its trip path cache in JavaScript.** `trip_path::with_trip_paths` is in the core and the uniffi binding, and the web binding exports no `withTripPaths`: the page's cache holds the page's own objects, which a round trip through the module would only copy. The conformance suite runs the cache's cases where an entry's trip path module holds `withTripPaths`.
- **The web binding refuses a few programmer errors otherwise than the JavaScript.** Each is a call no caller makes, and both refuse it. A routing snapshot decoder handed anything but an `ArrayBuffer`, a detached one included, throws `AssertionError`, where the JavaScript throws a `TypeError` or refuses a short view as `invalidHeader`; the callers on the facade hand the `ArrayBuffer` of `Response.arrayBuffer()` (`assets/js/saved_snapshots.js`, `assets/js/where_to_files.js`). `decodeTripPath` checks that `points`, `stops`, and `trip_id` are text before it decodes, so a path with several faults fails on another of them; no web module calls it, and the event's fields are JSON strings. `tripPathOf` refuses a stop distance that is no number, where the JavaScript compares what it is given; its callers build the stops from decoded numbers (`assets/js/core/trip_path_shard.js`). The walk's exports refuse a position column that is no `Int32Array`, where the JavaScript reads any array-like; its callers hand the columns `decodePositions` returns. They refuse a rule, a coordinate of the position, or a reached stop's `stop` or `streetM` that is no number, and `streetMetersMaxOf` refuses a `walkStreetMetersMax` that is neither a number nor absent, where the JavaScript writes the value into its message or compares it. `startsFromStreets` orders a reached stop whose `streetM` is NaN, or whose `stop` is NaN where its `streetM` equals another's, as `total_cmp` orders the NaN: after every number where its sign is positive and before every number where it is negative, where the JavaScript's order is its engine's sort's own. The engine's exports refuse a column that is no typed array of the type the routing snapshot decoders return for it, or that `createEngine` returns for `tripSlot` and the link offsets, `Int32Array`, `Uint32Array`, `Uint16Array`, or `Uint8Array`, where the JavaScript reads any array-like, a `stopCount` or `tripCount` that is no whole count, and a `minimumTransferS`, a query's `target`, `departureS`, or `arrivalS`, an origin's `stop`, or a start's `stop` or `walkS` that is no number, where the JavaScript writes the value into its message or compares it; they read every field of a query before the core checks any, so a query with several faults fails on the first the binding refuses, and they read the start stops by iterating them, where the JavaScript reads their `length` first. A failure's message from the binding's own checks names the binding, where the JavaScript's would come from the engine.
- **The math exists in both cores.** `assert.js` and the four modules of `math/` stay in JavaScript beside their Rust port, since the shell's per-frame motion modules call them on every frame and cross into WebAssembly on none. The conformance suite under `tools/conformance/` runs the shared cases of `test/fixtures/math/` against the JavaScript and through the WebAssembly binding in three browsers, and `cargo test` runs the same cases against `gobusgo-core`, so the two copies stay equal; a change to one is made to the other in the same commit.
- **wasm-bindgen moves in lockstep.** The crate is pinned exactly in `Cargo.toml`, and the command that reads its output in `mise.toml` and as the `Dockerfile`'s `WASM_BINDGEN_VERSION`; the three change together.

## Files

- `Cargo.toml`: the workspace, its shared dependencies, its lints, and its release profile.
- `rust-toolchain.toml`: the one pin of the compiler, its components, and the `wasm32-unknown-unknown` target; the `Dockerfile`'s `RUST_VERSION` changes with it.
- `clippy.toml`: the lints' allowances inside tests.
- `gobusgo-core/`: the logic. `core/gobusgo-core/src/assert.rs` holds the assertions, and `core/gobusgo-core/src/math/` the math, a module for each JavaScript module of `assets/js/core/math/` it ports, whose functions take an options struct where they take two arguments of one type or three or more, as the engineering style guide asks, and one argument bare: `tangent_plane` takes the latitude where the JavaScript's `tangentPlane` takes `{referenceLatitudeDegrees}`, and `distance_meters` takes a `Between` where the JavaScript's takes two positions. `core/gobusgo-core/src/routing_snapshot.rs`, `core/gobusgo-core/src/packed_container.rs`, and `core/gobusgo-core/src/trip_path.rs` hold the readers, which take a file's bytes or an event's text and return the records or a refusal, over the little-endian reads of `core/gobusgo-core/src/bytes.rs`; a count a file declares bounds every loop and is held to the file's length before anything is allocated, and an option a reader compares with a header's number is a double, as the JavaScript compares it. `core/gobusgo-core/src/routing_engine.rs` holds the engine, built once into an `Engine` that owns its columns, each stop's walking links out and in as offsets, the links in ordered by the stop they reach, and each connection's trip numbered densely; `route` and `route_arriving_by` run over an `EngineView`, those columns borrowed, whose stop count is one less than its link offsets, which a binding can make from arrays it holds without building the links again. A query's stops, departure or arrival, and walks are doubles, as the JavaScript compares and writes them; a label stores each time as the JavaScript's `Int32Array` does, its `ToInt32`, truncated and wrapped modulo 2^32, and compares a new time with the stored one as a double, a leg reads its duration back through the same `ToInt32`, and a query arriving by a time holds each start stop's walk through it, so a half-second minimum transfer boards at an equal departure, a departure of 2^31 is stored as -2^31, and a walk of 2^31 seconds reads back as -2^31 on its leg, as in the JavaScript, and the walk from the position of a journey arriving by a time is the query's own, whole, as the JavaScript's leg carries it; and an origin of a kind `OriginKind::named` does not name is `Origin::Unknown`, which `route` and `route_arriving_by` refuse in the JavaScript's order and with its message. `core/gobusgo-core/src/routing_walk.rs` holds the walk, whose rules, stops, and walk seconds are doubles, as the JavaScript compares and writes them into a refusal's message; `walk_basis_of` takes a manifest's `walkBasis` where it is text, and `WalkBasis::named` reads a basis's name and `WalkBasis::refuse_unknown` refuses a value that is not text, each with the JavaScript's refusal, so a binding parses neither. `tests/conformance/` runs the shared fixtures' cases, with a reader of the JSON they hold in `core/gobusgo-core/tests/conformance/json.rs`, since the core takes no crate.
- `gobusgo-core-wasm/`: the wasm-bindgen binding, built as a `cdylib` for the web and an `rlib` for its native tests. Each export takes the arguments of the JavaScript function of the same name, an options object read through its properties, and a constant crosses as a function, so `tools/conformance/webassembly_core.mjs` only names them.
- `gobusgo-core-ffi/`: the uniffi binding, built as a `cdylib` for Android, a `staticlib` for iOS, and an `rlib` for its native tests. A record or enum of the core crosses as the core's own type through a `#[uniffi::remote]` restatement of it, which the compiler refuses where its fields or variants differ from the core's, and a type alias gives it the name Swift and Kotlin know it by where the two differ (`SnapshotRefusal`, `SnapshotPositions`, `PathPoint`, `PathStop`, `WalkStart`, `WalkCandidate`). A record the core holds only as borrowed text or a borrowed file (`Ordered`, `EncodedPath`, `Near`), one the core holds with a borrowed origin or with a count or an index as a `usize`, which uniffi does not pass (`EngineInput`, `Origin`, `Query`, `QueryArrivingBy`, `Leg`, `Journey`, `JourneyArrivingBy`, each count and index crossing as a `u32`), and the results that exist only in the binding (`TripPath` and the outcome enums), are declared in the binding with uniffi's derives. `RoutingEngine` is the binding's one object, holding the engine.

## Build

`mix gobusgo.assets.core`, the first step of `mix assets.build` and `mix assets.deploy`, builds `gobusgo-core-wasm` for `wasm32-unknown-unknown` in release and runs `wasm-bindgen --target web` over it, writing `priv/static/assets/core/gobusgo_core.js` and `priv/static/assets/core/gobusgo_core_bg.wasm`. The loader is an ES module whose default initialization fetches the WebAssembly from beside its own address. Measured on 2026-11-13: the module is 37,476 bytes, and the image is 93,841 bytes larger than without the core. Measured on 2026-11-14 with the assertions and the math (GOB-425): the module wasm-bindgen writes, `gobusgo_core_bg.wasm`, is 106,684 bytes, 51,754 gzipped, up from 19,646 and 7,951 with `core_version` alone, and cargo's is 156,819, up from 37,476. `mix gobusgo.assets.core` drops the module's name and producers sections, which take 20,754 bytes of it. Writing a failure's numbers as `String` writes them takes Rust's precision formatting, about 18,900 bytes and 14,800 gzipped of the module. Measured on 2026-11-14 with the routing snapshot and trip path readers in the binding and the packed container in the core (GOB-426): `gobusgo_core_bg.wasm` is 134,729 bytes, 61,419 gzipped, up from 106,684 and 51,754, and cargo's is 205,435, up from 156,819. Measured on 2026-11-24 with the walk (GOB-427): `gobusgo_core_bg.wasm` is 157,097 bytes, 69,551 gzipped, up from 134,729 and 61,419, and cargo's is 238,099, up from 205,435; both rankings of the walk sort one type, since a stable sort's instance for a second type takes about 11 KB of the module. Measured on 2026-11-24 with the engine in the binding (GOB-427): `gobusgo_core_bg.wasm` is 210,506 bytes, 87,788 gzipped, up from 157,212 and 69,622 at the commit before, and cargo's is 308,955, up from 238,238.

## Checks

From `core/`, as CI's `core` job runs them:

```sh
cargo fmt --all --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo build --locked --release --package gobusgo-core-wasm --target wasm32-unknown-unknown
```

`cargo test` runs the conformance cases of `test/fixtures/math/`, `test/fixtures/routing/v2/`, `test/fixtures/routing/walk-v1/`, `test/fixtures/routing/engine-v1/`, `test/fixtures/packed/core-v1/`, and `test/fixtures/one_bus_away/trip_path/` that the browser suite runs, the packed container's against the Rust alone. `node test/scripts/core_binding_check.mjs`, after `mix gobusgo.assets.core`, calls `coreVersion` through the web loader and compares it with the workspace's version; CI's `assets` job runs it. The conformance suite runs the binding in three browsers, after `mix gobusgo.assets.core`, as `assets/AGENTS.md` ("Checks") describes; CI's `conformance` job runs it.
